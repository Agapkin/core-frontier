# Stage 02.4.5-A — Mobile Fix Pack / Input & Layout Stabilization

## Цель этапа

Stage 02.4.5 успешно разделил UI-слой на модули и убрал старый монолитный `js/ui.js`.

Однако тестирование на iPad и iPhone показало, что после архитектурной разрезки остались критические mobile UX и input-проблемы.

Цель Stage 02.4.5-A:

- стабилизировать строительство башен;
- исправить выбор клетки;
- исправить работу кнопки “Построить”;
- стабилизировать zoom;
- переработать mobile layout;
- улучшить landscape layout;
- уменьшить Codex на телефоне;
- привести controls к более удобной mobile-логике.

---

# Главные проблемы

## 1. Build Confirm Bug

Симптом:

- игрок выбирает клетку;
- клетка визуально подсвечивается;
- build overlay отображается;
- но при нажатии “Построить” появляется сообщение:
  “Сначала выбери клетку”;
- башня не строится.

Нужно проверить:

- `pendingBuildTile`;
- `selectBuildTile`;
- `confirmBuild`;
- canvas tap;
- DOM button click;
- pointer events;
- z-index;
- не сбрасывается ли выбранная клетка между тапом по canvas и тапом по кнопке.

---

## 2. Coordinate Mapping Instability

Симптом:

- клетка выбирается не совсем там, куда нажал игрок;
- особенно заметно на телефоне и планшете;
- при zoom ошибка ощущается сильнее.

Нужно проверить:

- `screenToWorld`;
- `screenToTile`;
- `worldToScreen`;
- `camera.zoom`;
- canvas bounding rect;
- Safari viewport;
- safe-area;
- mobile browser offsets.

---

## 3. Zoom Stabilization

Симптом:

- zoom работает;
- pinch zoom работает;
- кнопки +/- работают;
- но zoom можно “сбить” в неудобное состояние;
- нижняя кнопка “100%” не показывает текущий zoom;
- верхний zoom indicator обновляется, нижний — нет.

Нужно решить:

- либо убрать нижний процент;
- либо сделать динамическую кнопку;
- либо заменить кнопку “100%” на простую кнопку reset zoom.

---

## 4. Codex Mobile Layout

Симптом:

- Codex открывается;
- но на телефоне закрывает почти весь экран;
- мешает gameplay;
- выглядит как слишком крупная панель для mobile.

Нужно:

- уменьшить размер Codex;
- сделать компактный режим;
- ограничить высоту;
- возможно, сделать scroll внутри панели;
- отделить Codex от gameplay area.

---

## 5. Landscape Layout

Симптом:

- в горизонтальном режиме панели перекрывают карту;
- wave status занимает слишком много места;
- bottom controls мешают обзору;
- gameplay area уменьшается.

Нужно:

- сделать отдельный layout для landscape;
- уменьшить панели;
- перенести controls к краям;
- освободить центр карты.

---

## 6. Controls Placement

Симптом:

- кнопки “Башня”, “Волна”, “Codex”, “Меню” расположены неидеально для mobile;
- action-кнопки должны быть ближе к рабочему пальцу;
- информационные кнопки должны быть отделены от боевых действий.

Предварительное направление:

- “Башня” и “Волна” ближе к правому пальцу;
- speed controls рядом с action buttons;
- zoom controls отдельно;
- Codex и Menu компактно и отдельно;
- portrait и landscape могут иметь разные схемы.

# Developer Note — проблема повторных выдач кода и новый anti-regression workflow

Во время Stage 02.4.5-A снова проявилась проблема: кодовые файлы были выданы не с первой попытки.

Причина оказалась не в самом ТЗ, а в недостаточной технической разметке актуального ZIP перед написанием кода.

Stage-файл описывает цель и направление, но не гарантирует, что GPT автоматически учтёт:
- фактическое содержимое текущих файлов;
- реальные DOM id;
- порядок подключения скриптов;
- скрытые зависимости между модулями;
- состояние старых полей в state.js;
- какие функции уже существуют, а какие должны быть созданы;
- какие файлы ожидают друг друга.

## Выявленная проблема

При первой подготовке fix pack возник риск несовпадения между:
- index.html;
- js/ui/layout.js;
- js/game.js;
- js/systems.js;
- js/ui/controls.js;
- js/ui/panels.js.

Например:
- layout.js ожидал элементы HUD, которых ещё не было в index.html;
- updateTopbarVisibility искал id, которого не было в HTML;
- часть layout-полей существовала в старом виде;
- некоторые изменения требовали дополнительного файла, который изначально не был включён в комплект.

## Новый обязательный workflow

Перед любой кодовой выдачей GPT должен выполнять отдельный технический проход по актуальному ZIP.

Новый порядок:

1. Сначала создаётся stage-файл с целью, проблемами и ожидаемым результатом.
2. Затем загружается актуальный ZIP репозитория.
3. GPT читает фактические файлы.
4. GPT НЕ выдаёт код сразу.
5. Сначала GPT формирует technical implementation map:
   - список затрагиваемых файлов;
   - текущие функции в каждом файле;
   - новые функции, которые будут добавлены;
   - функции, которые будут изменены;
   - DOM id и HTML-элементы, на которые опирается код;
   - глобальные state-поля, которые используются;
   - зависимости между файлами;
   - порядок подключения;
   - риски регрессии.
6. После этого GPT формирует финальный список файлов.
7. Только потом GPT выдаёт код полными файлами.
8. После выдачи всех файлов GPT обязан выполнить self-check:
   - нет ли потерянных функций;
   - совпадают ли DOM id;
   - нет ли повторных объявлений;
   - все ли вызываемые функции существуют;
   - не требуется ли дополнительный файл;
   - совпадает ли порядок подключения в index.html.
9. Пользователь вносит файлы только после подтверждения целостности.
10. После внесения пользователь загружает ZIP, и GPT проводит финальную проверку.

## Новое правило

Запрещено переходить от stage-ТЗ сразу к коду.

Между ТЗ и кодом обязательно должен быть промежуточный шаг:

Technical Implementation Map.

## Цель правила

Снизить количество повторных выдач кода и избежать ситуации, когда файлы приходится переписывать по второму кругу.

Проект уже стал многомодульным, поэтому любые изменения должны выполняться dependency-aware способом, а не только по смыслу задачи.

## Итог

Stage 02.4.5-A фиксирует новый инженерный принцип проекта:

Сначала stage-ТЗ.
Потом ZIP-анализ.
Потом technical map.
Потом code output.
Потом self-check.
Потом manual replacement.
Потом ZIP validation.

Даже если механика уже работает,
новый игрок не понимает gameplay flow без подсказок.

# Основные замечания тестировщика

## 1. Непонятно как запускать волну

Игрок не понял кнопку запуска волны.

Кнопка не воспринимается как:
- “начать бой”;
- “следующий этап”;
- “запустить врагов”.

## Предложение

Сделать более читаемый call-to-action.

Возможные варианты:

- иконка ▶;
- мигающая кнопка;
- подсветка;
- tutorial arrow;
- pulse animation;
- текст:
  “Запустить волну”;
- временный onboarding hint.

---

# 2. Игрок не понял core loop

Без объяснения игрок не понял:

- что сначала строится башня;
- потом запускается волна;
- потом идёт защита базы.

Это означает, что current UX недостаточно объясняет flow.

---

# 3. Не хватает onboarding/tutorial system

Игрок сам предложил правильное решение:

нужно обучение.

Причём:
- не только при первом запуске;
- но и возможность пройти обучение повторно.

Это очень важное наблюдение.
