4. Operational Diagnostic Workflow

Step 1 — Source observation

Runtime/source file is inspected directly.
Potential pressure, growth and boundary signals are observed.

Examples:

* sequencing;
* state mutation;
* validation authority;
* render-only boundaries;
* callback bridges;
* shared mutable state;
* growth vectors.

⸻

Step 2 — Repository Map comparison

Observed signals are compared against:

01 → file authority/boundary layer
02 → function semantic layer
03 → topology/crossing layer
04 → surface/boundary layer

⸻

Step 3 — Cross-layer synthesis

Pressure does not emerge from one layer alone.
Pressure emerges from repeated cross-layer patterns.

⸻

Step 4 — 05 candidate emergence

If multiple pressure signals converge,
the area becomes a 05 candidate.

Important:

05 is not a generic “important things” layer.

⸻

Step 5 — 07 verification trigger

If Repository Map becomes insufficient,
direct source/runtime verification becomes required.

Meaning:

* additional source inspection;
* runtime-boundary validation;
* hotspot confirmation;
* gap detection.

⸻

Step 6 — 08 decision emergence

Only after verification,
possible split/refactor candidates may emerge.

Critical clarification:

05 does NOT automatically produce split decisions.
07 verification remains mandatory before 08.
