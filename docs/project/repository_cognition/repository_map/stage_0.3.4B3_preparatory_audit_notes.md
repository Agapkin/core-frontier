15. Что такое safe change
━━━━━━━━━━━━━━━━━━━━

Safe change
(безопасное изменение)
=
изменение,
при котором заранее понятно:

- какой смысл меняется;
- какие файлы затрагиваются;
- какие игровые системы могут пострадать;
- как проверить изменение;
- как откатить изменение.

Пример:

если изменяется tower placement
(размещение башни),

необходимо проверить:

| Что проверить | Почему |
|---|---|
| resources | хватает ли ресурсов и правильно ли они списываются |
| tile validation | можно ли ставить объект на выбранную клетку |
| rendering | появился ли объект визуально |
| collision | не сломались ли пересечения с другими объектами |
| UI update | обновились ли кнопки, панели и HUD |

Главный вывод:

safe change
не означает “изменение без риска”.

safe change означает:
риск заранее ограничен,
понятен
и проверяем.

16. Главный вывод о монолите
━━━━━━━━━━━━━━━━━━━━

Монолитная структура
(monolith)
не всегда является проблемой сама по себе.

Но в текущем проекте
монолитные runtime-файлы являются серьёзной проблемой
из-за выбранного способа разработки:

- код читается и изменяется через GPT;
- GPT работает через GitHub connector;
- connector имеет ограничения видимости файла;
- GPT имеет ограничения удержания контекста;
- большие файлы повышают риск неточного изменения.

━━━━━━━━━━━━━━━━━━━━
Почему монолит опасен именно для нашего workflow
━━━━━━━━━━━━━━━━━━━━

| Причина | Что это значит |
|---|---|
| Смешение смыслов | в одном файле живут gameplay, UI, rendering, input |
| Сильные пересечения | изменение одного участка может задеть соседние системы |
| Ограничения GitHub connector | GPT может не видеть весь файл или контекст целиком |
| Ограничения GPT-памяти | GPT теряет смысловые границы больших блоков |
| Риск широкого переписывания | вместо точечной правки GPT может начать переписывать лишнее |

━━━━━━━━━━━━━━━━━━━━
Практический вывод
━━━━━━━━━━━━━━━━━━━━

Для этого проекта
монолит опасен не потому,
что “монолит — это плохо”.

Он опасен потому,
что при GPT-assisted development
(разработке через GPT)

становится трудно:

- точно определить границы изменения;
- удержать весь смысл файла;
- изменить только нужный участок;
- проверить, что соседние системы не повреждены.

━━━━━━━━━━━━━━━━━━━━
Пример
━━━━━━━━━━━━━━━━━━━━

Если один runtime-file одновременно:

- обрабатывает input;
- управляет camera;
- запускает gameplay logic;
- обновляет rendering;
- вызывает UI;

то GPT может:

- изменить не тот участок;
- потерять связь между блоками;
- переписать больше, чем нужно;
- сломать работающую цепочку.
