# Stage 0.3.4B2 Design Doctrine Notes

## Purpose

This document captures stabilized architectural doctrine related to Repository Map evolution.

This document is:

* doctrine layer;
* crystallized reasoning layer;
* architectural interpretation layer.

This document is NOT:

* executable mutation contract;
* roadmap system;
* speculative ontology engine.

---

## 1. Repository Map as Blueprint

Repository Map is evolving from:

semantic mirror of current repository structure

toward:

architectural blueprint substrate.

Current source files are not always ideal future semantic boundaries.

Repository Map should support visibility of:

* operational topology;
* semantic boundaries;
* refactor pressure zones;
* future-safe structural domains.

---

## 2. Map Before Code Refactor

Runtime/source code should not be split directly from current structural complexity.

Safe refactor preparation requires:

1. map stabilization;
2. topology visibility;
3. surface visibility;
4. hotspot visibility;
5. risk visibility;
6. evidence routing stabilization;
7. bounded architectural planning.

Repository Map exists to support safer future mutation planning.

---

## 3. Source-Derived Values

Repository artifacts must not invent:

* gameplay values;
* entity properties;
* subsystem semantics;
* operational claims.

Values must come from:

* runtime/source verification;
* repository evidence routing;
* explicit approved design passes.

Speculation must remain outside canonical topology records.

---

## 4. Machine-Readable First

Human-readable structure alone is insufficient.

Repository artifacts should remain:

* parse-safe;
* machine-readable;
* scanner-readable;
* agent-readable.

Operational priorities include:

* stable ids;
* stable field structure;
* bounded vocab;
* centralized routing;
* minimized duplicated addressing.

---

## 5. Centralized Routing

Repository Map should prefer centralized routing patterns over duplicated paths and ad hoc wording.

Preferred model:

record
→ centralized ref/router
→ source authority

06 evidence routing is the first operational example of this doctrine.

---

## 6. Semantic Mud Avoidance

Stage contracts must remain operationally bounded.

Do NOT mix:

* executable scope;
* debt tracking;
* architectural doctrine;
* future roadmap speculation;
* raw reasoning archives.

Different artifact classes must remain separated.

---

## 7. Future Runtime Data Scalability

Future runtime domains may eventually require structured data-oriented topology support.

Current doctrine:

preserve future extensibility without premature architecture expansion.

B2 does NOT implement runtime catalog systems or data orchestration frameworks.

---

## 8. Reasoning Swamp vs Crystallized Artifacts

Chat branches and reasoning archives represent:

* raw reasoning substrate;
* semi-processed exploration;
* historical cognition flow.

Canonical repository artifacts should contain only:

* bounded outputs;
* operationally useful structure;
* crystallized topology;
* source-confirmed records;
* stabilized doctrine.

Repository Map should evolve toward:

compressed operational cognition.

Repository artifacts should remain operationally bounded.

---

## 9. Semantic Density Awareness

Large artifacts become dangerous not only because of raw file size, but because of:

* semantic density;
* connector truncation;
* cognition overload;
* hidden unread sections;
* parser instability;
* reviewability collapse.

Operational readability and bounded semantic domains are more important than raw line count alone.

Repository Map split planning should consider:

* semantic overlap;
* cognition pressure;
* parser safety;
* connector limitations;
* reviewability.
